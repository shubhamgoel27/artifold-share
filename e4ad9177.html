Comment-Likelihood Prediction Platform

Serve a black-box model that scores P(user comments on a post). The model is given; the design problem is the infrastructure around it — feature pipelines, a dual-layer feature store, training and serving paths, and the production concerns that keep them honest.

01

Data sources & event logging

Everything downstream — labels, features, monitoring — is reconstructed from the event log. Get the log right and the rest is tractable; get it wrong and skew and leakage are baked in.

Events to log
  • Impressions — (user_id, post_id, surface, ts, rank_position, request_id)
  • Engagements — comment / like / dwell, each with its own timestamp; comment-with-ts is the label source
  • Context — device, locale, network, time-of-day, experiment buckets
Data-quality contract
  • Idempotent ingestion — dedupe on event_id (effectively-once)
  • Late events — watermarks; reconcile the lake after the watermark closes
  • Schema evolution — versioned, backward-compatible schemas (Avro/Protobuf + registry)

Transport splits by use: a stream bus (Kafka / PubSub) carries events to real-time feature computation, while the same events land in a data lake / warehouse (S3 + Iceberg/Hive, or BigQuery/Snowflake) as the durable source of truth for training and backfills.

Feature engineering & the feature store

The model is a black box, so the leverage is here: feature correctness, freshness, and offline/online consistency. The store is two layers behind one set of definitions.

Two layers, one definition
  • Offline store — historical features over the lake, for training-set construction and backfills
  • Online store — low-latency KV (Redis / Cassandra / Bigtable) for serving, multi-get by key
  • Feature repo — each transform defined once, compiled to a batch job (offline) and a streaming job (online)
Streaming aggregates & TTL
  • Windowed features via Flink/Spark Streaming — 10m / 1h / 24h counts, unique authors, comment rate
  • Effectively-once updates, deduped by event_id
  • TTL by volatility — hot 1h/24h counters expire in hours–days; cold keys evicted to bound memory
Killing training/serving skew (the headline risk)

Three mechanisms, not vibes: (1) single feature definitions compiled to both runtimes — never re-implemented; (2) point-in-time correctness — a training row for an impression at time t may only read feature values available at t, preventing label leakage; (3) feature versioning — (name, version) pinned, and each model locked to a feature-set version so retraining can't silently drift.

03

Training pipeline & dataset versioning

Reconstruct each example as the model would have seen it at impression time, attach the realized label, and make the whole artifact reproducible.

Labels & dataset
  • Positive if a comment occurs within the horizon (24h) after the impression; negative otherwise
  • Label per impression; downsample negatives and re-weight to manage the heavy class imbalance
  • Build rows by joining impressions to point-in-time feature snapshots; emit (features, label, metadata: ts, surface, experiment)
Eval, calibration & registry
  • Metrics — AUC / PR-AUC, plus calibration (Brier, reliability curve), sliced by surface & locale
  • Calibrate probabilities (Platt / isotonic) since downstream ranking assumes them
  • Registry records feature-set version, training data range, code commit, eval report; promote dev → staging → prod
04

Online inference architecture

Feed ranking scores ~100 candidates per request under a tight budget. The whole game is amortizing feature I/O and model compute across the candidate set, with fallbacks when a dependency stalls.

Request flow — feed ranking
1

Request

User opens feed; request carries user_id + context.

2

Candidate gen

Returns K post_ids (retrieval / heuristics).

3

Feature fetch

User features once; batched multi-get for K posts + interactions.

4

Score

Model server micro-batches the K candidates in one forward pass.

5

Rank

Sort by score + business rules; return feed.

Feature retrieval — avoid K round-trips
  • Fetch user features once per request, not per candidate
  • Batch multi-get post + interaction features for all K keys
  • In-process LRU cache for hot post features (popular posts dominate)
Model serving & safety
  • Dedicated server (TF-Serving / TorchServe / gRPC), autoscaled; CPU + batching is usually enough for ranking
  • Timeouts + fallbacks — on feature-store timeout, use default/cohort features or a simpler heuristic model
  • Circuit breakers isolate slow dependencies; degrade, don't fail the request

Budget is an assumption to defend, not a measurement. Scoring dominates → micro-batching is the first knob; feature I/O is second → multi-get + cache.
Batch path — notifications & nightly jobs

Not everything is request-time. Candidate scoring for notifications and nightly precompute run as Spark/Beam batch inference, writing scores to a store the product reads — trading latency for throughput where the surface allows it.

05

Monitoring, retraining & rollout

Labels arrive late (a comment may land 24h after the impression), so monitoring runs in two tiers: immediate signals that need no labels, and delayed signals that do.

Data monitoring (no labels needed)
  • Feature freshness lag — stream delay per feature group
  • Missing / null rate per feature; alert on spikes
  • Distribution drift — online feature histograms vs the training baseline
Model monitoring
  • Prediction drift — score mean / quantiles over time
  • Calibration drift — once labels mature
  • Business KPIs — comment rate, session time, negative feedback
Retraining triggers
  • Scheduled — daily / weekly cadence
  • Triggered — drift threshold breach or KPI regression
  • Backfill on logging outages before the next train
Experimentation & safe rollout
  • User-level A/B with guardrails: latency, error rate, abuse/spam metrics
  • Shadow → canary → ramp; auto-rollback on guardrail breach
  • Interleaving or bandits optional for ranking comparisons

  • Spam / adversarial shift — anti-abuse features + drift alarms on adversarial distributions
Privacy & compliance
  • PII minimization, access controls, retention limits on raw events
  • Honor deletion / opt-out down through the feature store
What the interviewer is actually probing
  1. Can you articulate offline/online parity and prevent label leakage (point-in-time)?
  2. Can you design a feature store with windowed aggregates and a sane TTL strategy?
  3. Can you hit the latency budget with batching, caching, and dependency isolation?
  4. Can you propose two-tier monitoring, retraining triggers, and safe rollout?
